# Microphone capture for continuous Go recording

Archived September 30, 2026 research for maintainers. Version comparisons, approval proposals, indexed naming recommendations and open questions are historical findings, not current requirements. Read the [repository instructions](../../../../../AGENTS.md) and [contributor instructions](../../../contributing.md) for current decisions. SDK citations retain the recorded header names and line numbers without machine-local links.

Research notes for the project coordinator. Checked 2026-09-30; candidate dependencies remain unapproved and were not installed. User confirmed **macOS only, microphone plus computer playback**. Native SDK sources below are installed Apple headers obtained from `xcrun --show-sdk-path`, not inferred API contracts.

Host inspection log: `sw_vers` returns `ProductVersion: 26.6.2`, `BuildVersion: 25G83`. This is the inspected host, not proof of completed recording/device recovery tests.

## Which capture library best fits a single executable and low CPU?

### Takeaway

For the full microphone-plus-playback requirement, propose **native Core Audio process taps and a private HAL aggregate through project-owned cgo/C/Objective-C**, minimum macOS **14.2**. No mature, verified Go library supplies both streams with the required timestamp, format and loss diagnostics. Malgo ranks first for microphone-only capture but cannot supply native macOS playback capture.

### Cited Findings

- Apple process taps capture selected processes or process groups and can feed an aggregate device as an input. `AudioHardwareCreateProcessTap` and `CATapDescription` enable this natively, without installing a loopback driver. Apple's sample requires macOS 14.2+. Local `AudioHardwareTapping.h:44` independently declares `API_AVAILABLE(macos(14.2))`. — [Apple process tap sample](https://developer.apple.com/documentation/coreaudio/capturing-system-audio-with-core-audio-taps); installed Apple header (`AudioHardwareTapping.h:44`)
- Local `CATapDescription.h` defines mono/stereo global tap constructors excluding specified process objects; all other audio-producing processes are included. It exposes private visibility and muting separately. A recorder should use unmuted capture so playback continues normally. — [Apple CATapDescription](https://developer.apple.com/documentation/coreaudio/catapdescription); installed declarations (`CATapDescription.h:58`)
- Miniaudio documents its loopback device API as **WASAPI-only**, so the bundled macOS Core Audio backend does not solve computer playback capture. — [official low-level API](https://miniaud.io/docs/manual/index.html)
- **ScreenCaptureKit:** Apple's current sample requires macOS15 and captures `.audio` and `.microphone` outputs in separate handlers; first run requests Screen Recording permission. Local SDK establishes audio output support from macOS13, microphone output and `captureMicrophone` from macOS15. System-audio PCM obeys configured rate/channels, while microphone PCM uses its selected device's **native format**. — [Apple capture sample](https://developer.apple.com/documentation/screencapturekit/capturing-screen-content-in-macos); installed format and availability contract (`SCStream.h:29`)
- **AudioTee** uses process taps, macOS14.2+, and Swift5.9; public API captures system playback only, with microphone work described as internal. Repository API snapshot: 92 stars, 26 forks, pushed 2026-03-31 and no detected license (`license: null`). This is an external executable/Swift project rather than an approved embedded Go library. — [upstream README](https://github.com/makeusabrew/audiotee); [repository API](https://api.github.com/repos/makeusabrew/audiotee)
- **tmc/apple** supplies autogenerated, cgo-free framework bindings using purego dynamic loading; 28 stars, 3 forks, created 2025-11-16, pushed 2026-09-07, MIT. It includes a systap example, but that callback allocates a byte slice, takes a mutex and writes to disk; the example does not preserve input timestamps. Generated public tap/device functions panic when dynamic symbols fail to resolve. These are evidence against adopting the example's capture lifecycle for this task, rather than evidence that all bindings are unusable. — [upstream README](https://github.com/tmc/apple); [repository API](https://api.github.com/repos/tmc/apple); [systap example](https://raw.githubusercontent.com/tmc/apple/main/cmd/systap/main.go); [generated function handling](https://raw.githubusercontent.com/tmc/apple/main/coreaudio/functions.gen.go)
- **malgo:** requires cgo; its README says no additional link libraries are required on Windows/macOS. Linux/BSD use system link libraries; inspect its exact cgo directives rather than equating this with a fully static executable. Supported macOS backend is Core Audio. The repository contains `miniaudio.c` and `miniaudio.h`. — [malgo README](https://github.com/gen2brain/malgo); [build directives](https://raw.githubusercontent.com/gen2brain/malgo/master/miniaudio.go)
- Verified GitHub API snapshot: malgo has **428 stars, 64 forks**, latest tag **v0.11.26**, pointing to `4de8979ec9496b6fbb45d10625a087d8cc011a62`; last commit 2026-08-18. The preceding August changes optimize the miniaudio build and disable the unexposed high-level API; a May change exposes negotiated internal device properties. — [repository API](https://api.github.com/repos/gen2brain/malgo); [tags API](https://api.github.com/repos/gen2brain/malgo/tags?per_page=5); [recent commits API](https://api.github.com/repos/gen2brain/malgo/commits?per_page=5)
- malgo **v0.11.26 embeds miniaudio 0.11.25**, as verified by `MA_VERSION_MAJOR/MINOR/REVISION` in its vendored header. The wrapper and native library have different patch numbers. — [version-pinned header](https://raw.githubusercontent.com/gen2brain/malgo/v0.11.26/miniaudio.h)
- Miniaudio's low-level API delivers PCM asynchronously and can capture without the playback/mixing engine. It can convert sample format, rate and channel count; requesting native configuration avoids its conversion overhead. Its conservative performance profile mainly changes default buffer sizing; buffer size is a hint ultimately selected by the backend. — [official manual](https://miniaud.io/docs/manual/index.html); [configuration contract](https://raw.githubusercontent.com/gen2brain/malgo/v0.11.26/miniaudio.h)
- **gordonklaus/portaudio:** build requires PortAudio development headers/libraries. Binding uses `#cgo pkg-config: portaudio-2.0`, rather than bundling native PortAudio source. API snapshot: **844 stars, 109 forks**. Latest commit 2026-02-03 only changes a README link; previous feature commit is 2025-02-06, exposing device indices. — [README](https://github.com/gordonklaus/portaudio); [source directives](https://raw.githubusercontent.com/gordonklaus/portaudio/master/portaudio.go); [repository API](https://api.github.com/repos/gordonklaus/portaudio); [commits API](https://api.github.com/repos/gordonklaus/portaudio/commits?per_page=4)
- **Native Core Audio:** `AudioDeviceCreateIOProcID`/`AudioDeviceStart` supply device callbacks, and `AudioObjectAddPropertyListener` registers notifications for property changes. Apple exposes `kAudioHardwarePropertyDefaultInputDevice`. — [Core Audio listener API](https://developer.apple.com/documentation/coreaudio/audioobjectaddpropertylistener(_:_:_:_:)); [default-input property](https://developer.apple.com/documentation/coreaudio/kaudiohardwarepropertydefaultinputdevice)
- **graphaelli/audiotap:** an existing macOS Go/Core Audio candidate automatically follows default microphone changes and embeds C/Objective-C source via cgo. Its Go package uses a C ring buffer and self-pipe so the real-time callback does not enter Go. Links only OS frameworks and Objective-C runtime, not a separately installed `libaudiotap.dylib`. Package documentation requires macOS 14.2+, Go 1.22+. API snapshot: created 2026-02-13, pushed 2026-04-16, **0 stars, 1 fork**, Apache-2.0 license. — [Go README](https://raw.githubusercontent.com/graphaelli/audiotap/main/go/README.md); [Go link directives](https://raw.githubusercontent.com/graphaelli/audiotap/main/go/audiotap.go); [embedded source wrapper](https://raw.githubusercontent.com/graphaelli/audiotap/main/go/cgo_audiotap_mic.c); [repository API](https://api.github.com/repos/graphaelli/audiotap)
- **Pure Go alternatives:** Oto documents playback, players and `io.Reader` sound sources; it is not a verified capture candidate. `jfreymuth/pulse` implements PulseAudio's native protocol in pure Go, supports recording, and reports missing shared-memory support. It connects to a PulseAudio server rather than directly providing a native macOS microphone backend. — [Oto README](https://raw.githubusercontent.com/ebitengine/oto/main/README.md); [pulse README](https://github.com/jfreymuth/pulse)
- `MarkKremer/microphone` wraps PortAudio for Beep, retains the installed PortAudio requirement and has 47 stars in the inspected page; it does not remove that dependency. — [upstream README](https://github.com/MarkKremer/microphone)

### Inferences

- A single distributable macOS executable is compatible with embedded cgo libraries and links to macOS frameworks. It does not mean a standalone static executable without the operating system's libraries. Verify the final binary's linkage after the dependency is approved.
- For microphone-only capture, malgo's recent native-build and device-property work is more relevant than PortAudio's higher star count. Stars indicate attention, not recording reliability. Full requirements instead favor a native process tap implementation with explicit metadata handling.
- Larger capture buffers and avoiding unnecessary conversion are promising CPU controls, but must be measured on target hardware. No source establishes a defensible CPU percentage for this application.
- **Concrete capture proposal:** cgo/C/Objective-C binding to Apple CoreAudio, AudioToolbox, CoreFoundation/Foundation and AVFoundation; no third-party capture module, helper executable, or installed virtual driver. Use a global unmuted private process tap plus the selected microphone in a private aggregate, with a declared clock master and native drift compensation. This aggregate is an app-local HAL object, destroyed by the app, not a persistent replacement for system defaults. Verify that tap/mic native rates can be configured compatibly; use Apple's AudioConverter for actual PCM rate/format conversion where necessary. Prototype this topology before claiming simultaneous device-switch correctness.
- ScreenCaptureKit is a supported alternative when minimum macOS15 and its permission/stream lifecycle fit the product; it still requires PCM metadata validation, resampling and timestamp alignment. No benchmark here establishes its CPU cost versus Core Audio taps.

### Gaps

- No mature, adopted pure-Go **native macOS microphone-plus-playback recorder** was verified. `tmc/apple` is a young framework-binding candidate, not a proven recorder implementation. Do not mistake pure-Go playback for capture support.
- Exact single-binary output and CPU usage remain unmeasured because dependencies are unapproved.
- Minimum macOS version remains a user decision: process taps require 14.2; ScreenCaptureKit unified mic capture requires 15. Capture device selection and mixing policy remain unresolved.

## Can capture recover from disconnects, default switches and stalls?

### Takeaway

Miniaudio has real Core Audio default-device rerouting, but neither its documentation nor malgo guarantees uninterrupted samples or reliable notifications for every failure. A captured-frame watchdog and an external restart mechanism are required to address silent callback stalls and blocking native teardown.

### Cited Findings

- Apple IOProc's `inInputTime` identifies acquisition time of the first input frame, independently of callback invocation time. `kAudioTapPropertyFormat` supplies the tap's actual ASBD; aggregate subTap drift compensation is enabled by `kAudioSubTapDriftCompensationKey`. These are native primitives for preserved timing, actual format and clock handling. — [IOProc API](https://developer.apple.com/documentation/coreaudio/audiodeviceioproc); installed timestamp contract (`AudioHardware.h:761`); tap format contract (`AudioHardware.h:2013`); drift compensation key (`AudioHardware.h:1882`)
- Apple documents that aggregates can be private to the creating application process and that Core Audio handles synchronization. Its archive states all component devices must share a sampling rate and mixable streams; treat old aggregate restrictions cautiously because the modern process-tap sample adds new tap sources. AudioConverter supports PCM sample-rate/bit-depth conversion using explicit input/output ASBDs. — [Apple aggregate and converter overview](https://developer.apple.com/library/archive/documentation/MusicAudio/Conceptual/CoreAudioOverview/ARoadmaptoCommonTasks/ARoadmaptoCommonTasks.html)
- **Startup trap:** local Apple header states nonzero `kAudioAggregateDeviceTapAutoStartKey` makes `AudioDeviceStart` wait until a tapped application produces its first audio. This semantic can block startup during silence; the key is not a generic flag to start capture immediately. — installed tap-auto-start contract (`AudioHardware.h:1630`)
- malgo initializes the default device when device ID is nil; enumerated first device must not be assumed to be default. Its Go callback API exposes `Data` and `Stop`. Config has an untyped C `NotificationCallback` pointer, but the wrapper's callback setup does not expose a typed Go notification hook. Data callback wraps C input memory with `unsafe.Slice`, so it is borrowed callback memory. — [device implementation](https://raw.githubusercontent.com/gen2brain/malgo/master/device.go); [device config](https://raw.githubusercontent.com/gen2brain/malgo/master/device_config.go); [C callback declarations](https://raw.githubusercontent.com/gen2brain/malgo/v0.11.26/malgo.h)
- Native notification types include started, stopped, rerouted and interruption events; not every backend emits every event. Stopped does not fire on reroute. Device restart/uninitialization is forbidden inside the notification callback. Legacy Stop callback is deprecated upstream. — [notification contract](https://raw.githubusercontent.com/gen2brain/malgo/v0.11.26/miniaudio.h)
- Version-pinned Core Audio code registers default-input property listeners and calls internal reinitialization when defaults change; it restarts a previously started input AudioUnit and posts rerouted afterward. Critically, the preceding AudioUnit-stop handling includes a TODO about predicting whether Core Audio will switch after unplug, and skips the stopped notification in that path. — [Core Audio implementation, approximately lines 35349–35460](https://raw.githubusercontent.com/gen2brain/malgo/v0.11.26/miniaudio.h)
- malgo `Start` waits for worker startup and a mutex. `Stop` waits for the worker and may wait for the current audio fragment; `Uninit` calls native uninitialization. These APIs expose no context or timeout. — [lifecycle source](https://raw.githubusercontent.com/gen2brain/malgo/master/device.go)
- PortAudio's official HotPlug wiki describes its device-refresh/notification API as a work in progress on a hotplug branch; the proposed invariants require clients to refresh the device list and prohibit doing so from callbacks. Treat this design document as a proposal, not shipped binding functionality. — [PortAudio HotPlug wiki](https://github.com/PortAudio/portaudio/wiki/HotPlug)
- audiotap's microphone listener stops the previous IOProc then starts the new default device, but ignores the restart result. Its mic code stores requested `sample_rate` without querying/configuring the native stream rate or resampling; raw buffers are cast to floats and only channel conversion is performed. Its bridge drops oldest samples on overflow, discards native host timestamps, and exposes no overflow counter through the inspected Go API. — [mic source](https://raw.githubusercontent.com/graphaelli/audiotap/main/src/audiotap_mic.c); [bridge source](https://raw.githubusercontent.com/graphaelli/audiotap/main/go/bridge.c); [Go API](https://raw.githubusercontent.com/graphaelli/audiotap/main/go/audiotap.go)

### Inferences

- Copy borrowed callback samples into owned, bounded storage promptly; encoding, disk writes, logging and device lifecycle work should happen off the callback thread. Observe dropped-frame counts explicitly.
- Monitor **frame delivery**, not signal amplitude: quiet or all-zero samples are legitimate silence and should not trigger device resets. `IsStarted` plus Stop callback does not prove capture progress.
- Watchdog recovery inside one process cannot forcibly cancel an indefinitely blocked C call. A supervisor can terminate/restart the process using the same executable, but recovery necessarily loses uncaptured audio during the fault/restart interval.
- For native combined capture, retain source identity, input host/sample timestamps, native format and frame counts through the bounded queue. Establish one capture clock or explicitly reconcile streams by their timestamps; arrival order and equal buffer lengths do not establish synchronization. Validate stream layout so microphone samples and process tap samples are not accidentally interpreted as a single undifferentiated stereo buffer. Preserve diagnosed gaps rather than falsely claiming their silence is real audio.
- Do not recommend audiotap as production-ready for this requirement: rate negotiation and silent-loss diagnostics are materially missing in inspected source. Its architectural ideas do not establish correct recording behavior.

### Gaps

- USB/Bluetooth switching, OS sleep/wake, permission revocation, format changes and native callback stalls need actual target-platform tests. Upstream API/source inspection does not establish application behavior.
- There is no verified promise of gapless transition when default microphone changes. Literal never-stop recording cannot be proven from these libraries.

## What macOS permission and hardware conditions constrain recording?

### Takeaway

Microphone permission and macOS security controls are hard prerequisites regardless of library choice. A laptop's built-in microphone may be physically disabled when its lid closes, so “one mic is available” must mean an accessible capture source, not just an enumerated device.

### Cited Findings

- Apple requires `NSMicrophoneUsageDescription` for APIs accessing the device microphone; it is a user-facing reason for access. `NSAudioCaptureUsageDescription` is separately described for system audio capture. — [Apple microphone usage key](https://developer.apple.com/documentation/BundleResources/Information-Property-List/NSMicrophoneUsageDescription)
- Apple process tap sample explicitly requires `NSAudioCaptureUsageDescription`; starting an aggregate containing a tap triggers the system audio recording permission prompt. This is separate from microphone access. — [Apple process tap permissions](https://developer.apple.com/documentation/coreaudio/capturing-system-audio-with-core-audio-taps)
- Under Hardened Runtime, `com.apple.security.device.audio-input` enables microphone and Core Audio input access. Apple's documentation distinguishes the microphone sandbox entitlement. — [Apple Audio Input entitlement](https://developer.apple.com/documentation/BundleResources/Entitlements/com.apple.security.device.audio-input)
- Apple directs users to Privacy & Security → Microphone when audio-input recording lacks permission, covering built-in, USB microphones and external interfaces. — [Apple input permission support](https://support.apple.com/en-ie/102071)
- Apple silicon Mac laptops and T2-equipped Intel laptops physically disconnect the microphone when the lid is closed; software, including root/kernel privileges, cannot override that hardware disconnect. — [Apple Platform Security](https://support.apple.com/guide/security/hardware-microphone-disconnect-secbbd20b00b/web)
- audiotap's upstream README reports that `AudioDeviceStart` can block indefinitely when microphone permission is missing and a dialog cannot be presented, and documents a permission check before startup. This is upstream experience, not an Apple API guarantee. — [audiotap permission observations](https://raw.githubusercontent.com/graphaelli/audiotap/main/README.md)

### Inferences

- Verify permission acquisition separately for terminal-launched development, the built executable, and any LaunchAgent deployment; entitlement and purpose-string requirements should be part of the approved packaging design.
- Recovery must keep reporting and retrying when permission is revoked, but cannot manufacture microphone audio during that interval.
- Clarify whether closed-lid capture is required and, if so, confirm the user has an external microphone accessible in that state.

### Gaps

- Standalone CLI Info.plist embedding, signing and background permission identity need official packaging-source verification and a real LaunchAgent test before claiming reliable unattended launch. No exact packaging recipe is asserted here.
- Single-binary permission footnote: microphone and computer playback require separate macOS consent and purpose strings. A terminal test does not establish the permission identity of a standalone binary or its LaunchAgent process; verify with the built, signed executable on the inspected macOS 26.6.2 host. — [Apple usage key](https://developer.apple.com/documentation/BundleResources/Information-Property-List/NSMicrophoneUsageDescription); [Apple process tap consent](https://developer.apple.com/documentation/coreaudio/capturing-system-audio-with-core-audio-taps)
- Actual microphone authorization was not requested; research did not record audio or change system settings.
